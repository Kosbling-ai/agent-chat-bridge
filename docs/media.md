# Feishu media

For authorized P2P conversations, every Feishu message type proceeds to Codex. Text and rich-post text remain in the prompt. Standalone image, file, audio and video messages, plus `img`, `file`, and `media` nodes in rich posts, become ordered attachment metadata. The bridge attempts each downloadable resource independently and appends one Chinese attachment line per item, including its original name, duration, status, byte size, and absolute inbox path when downloaded. Stickers, share cards, merged forwards, interactive messages, and unknown types are represented as metadata instead of being rejected by the bridge. One failed attachment does not block the remaining attachments or the Codex turn.

Downloads use `messageResource`: images use `type=image`; files, audio, and video use `type=file`. Files are streamed below `<inbox>/<safe chat_id>/<safe message_id>/`. The original filename supplies only the extension and prompt metadata; the stored basename comes from the sanitized resource key. `feishu.mediaMaxBytes` is a hard per-resource limit, defaults to and cannot exceed 32 MiB, and aborts the stream and removes the partial file on overflow. `feishu.mediaDownloadTimeoutMs` defaults to 120000 ms and applies independently to resource retrieval. `feishu.mediaEnabled=false` preserves the attachment metadata but skips downloads.

Downloaded images are supplied to Codex as `localImage` input items after the leading text item. Other files remain absolute paths in the text attachment block because the app-server has no general local-file input item. A 2026-09-19 local probe found that app-server accepted a `localAudio` item, but the model could not read the valid PCM WAV content, so audio is intentionally not wired as `localAudio` and remains a local path in the attachment block: “app-server 接受 localAudio item 但模型未能读出内容，故暂不接线”。

This change is limited to the P2P inbound path. Group posts still keep only their text and group media remains ignored until the group-context follow-up change. Inbound files stay under the two-level inbox layout and are not scanned by the direct-child outbound scanner.

Bridge output remains separate: executor-produced attachment paths are sent from the outbox. P2P delivery is allowed, while groups must enable the `bridge` capability. Each outbound file is capped at 28 MiB. Images use Feishu image upload; other extensions use file upload. Successful sends delete the local source. A failed file remains and does not stop the text reply or another attachment.

These files and their internal outbox state are not exposed through an HTTP resource API. Tests use synthetic SDK clients and local temporary files; they do not establish real Feishu acceptance.
