# Computer Use through Feishu

Set `codex.computerUse` to `true` in the bridge configuration and restart the service. It defaults to `false` and is independent of `codex.requestUserInput`.

```json
{
  "codex": {
    "computerUse": true
  }
}
```

This fragment extends the existing `codex` object; keep its `bin`, `cwd`, `sharedHome`, and other settings.

## Prerequisites

The configured Codex installation/home must already provide the bundled `cua_repl` MCP runtime (Computer Use / unified-computer-use). The host's native Computer Use helper and required macOS permissions must be available to that runtime. This bridge option does not install a plugin, copy desktop credentials, create a browser transport, change managed app policy, or grant OS accessibility/screen-recording permissions. A working native-app approval does not prove that the separate browser/IAB transport is available.

Ordinary MCP calls already work through Codex. This feature adds the missing server-to-client `mcpServer/elicitation/request` response path for native app access. It was checked against the protocol generated by Codex `0.155.0-alpha.9.2` and the installed unified Computer Use runtime `26.915.31945`.

## Approval flow

When the CUA runtime asks to access an app, the initiating Feishu user receives an interaction card showing the app identifier, tool, risk and any warning. The user must select **拒绝** or **允许本次请求** and submit. There is no preselected approval and no permanent-approval option. An accepted result has no persistence hint (`_meta: null`); the bridge does not cache app approvals. The runtime can ask again on subsequent calls.

The card uses the existing durable user-input delivery and callback authorization: the actor, chat, message, job, request ID and item ID must match, and only one answer reaches the live Codex process. Superseded/expired requests, failed card delivery, disconnects and restarts never grant access. Restarted processes do not replay approvals from old cards. App access does not authorize every consequential action in that app; Codex's confirmation rules and managed policy still apply.

Only the bundled `cua_repl` server's recognized `computer-use` native app-access approval metadata with an empty object form is supported. Generic MCP forms, URL authorization, secret/user-verification challenges, computer audio and uncorrelated turns are not supported and are cancelled. Command/file approvals continue to follow the configured Codex approval policy.

## Verification

After deployment, ask the bot to read a harmless app window. Confirm the app identifier on the resulting card, choose an answer, and check the resulting tool output. Test denial as well as acceptance. A green `/health/ready` only shows component readiness; it does not prove an app was read or a browser page was loaded.

If no card appears, verify the option in that bot's actual `bridge.json`, its Codex home/plugin registration, and the installed runtime version. A Cloudflare page is a website verification issue, not a bridge approval failure. Do not work around managed or OS access denials.

## 中文说明

此开关补充的是 MCP 执行中向用户请求应用授权的通道，不影响已有普通 MCP 工具调用。用户在飞书卡片上明确选择允许或拒绝；不自动批准、不提供永久授权。沿用原交互卡片的身份校验、持久化和单次提交机制。

本机仍须安装可用的 Computer Use 插件及辅助程序，并具备系统权限。原生应用授权与浏览器连接是两条不同链路，需分别验证。当前不支持任意 MCP 表单、登录/验证码、录音或无法关联到活动轮次的请求。
